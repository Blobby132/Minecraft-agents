# Top technical risks

Status: **Proposed**. Ordered by how likely each one is to block the project, multiplied by how late we would find out. Each risk has an **early detection** step tied to a milestone.

| # | Risk | Impact | Early detection | Mitigation / alternatives |
|---|---|---|---|---|
| 1 | **The GPU path doesn't work on the RX 9060 XT under Windows.** Ollama's Windows ROCm list doesn't include RDNA4, Vulkan is the documented path, and community reports are mixed. The model might run on the CPU, or only partly on the GPU. | Inference 5–10× slower. The planner becomes unusable at real-time pace. | **M1 Spike A:** read `size_vram/size` from `/api/ps`, measure tokens/s and TTFT, and compare against a forced-CPU run (`OLLAMA_VULKAN=0`). The health check shows the GPU share live. | Update Ollama or the AMD driver. Try `GGML_VK_*` options. Switch to **LM Studio** (Vulkan llama.cpp) or a **llama.cpp server** (Vulkan build) behind the same `ModelProvider` interface. Use a smaller quant. |
| 2 | **VRAM contention with the Minecraft client** on the same 16 GB card. | The model is partly offloaded to the CPU (slow), or the game stutters. gpt-oss-20b (14 GB) almost certainly won't fit. | **Spike A runs twice**, with Minecraft closed and then open (documented steps). It records the model's `size_vram` and total dedicated GPU memory from Windows performance counters. | Use a smaller model or quant (QAT builds), a smaller `num_ctx`, a quantized KV cache (`OLLAMA_KV_CACHE_TYPE=q8_0` with flash attention, if Vulkan supports it), and lower Minecraft render distance. The benchmark scores VRAM fit explicitly. |
| 3 | **Small local models make poor or invalid decisions.** | The agent loops, idles or picks nonsense. | **M3 benchmark** on a fixed scenario set: valid-action rate, decision quality against expected-action sets, latency. A fuzz test feeds the parser random and broken JSON. | Schema-constrained decoding. Skill and item enums generated from the registry and minecraft-data. Short focused prompts. Few-shot examples. Repair and fallback. Reflexes cover urgent behaviour. A bandit re-ranker in M6. |
| 4 | **Latency mismatch:** seconds per decision against a 20 Hz world. | The bot stands still or dies while thinking. | Spike A gives TTFT and tok/s. M3 records the latency of every decision. | The layered design: reflexes and skills never wait on the model. Skills are long-running units. The planner is event-driven and asynchronous. Deadlines drop stale requests. |
| 5 | **Mineflayer plugins are stale.** pathfinder was last published in 2023, pvp and tool in 2022. pvp uses the deprecated `physicTick` event. | Getting stuck in pathing, door and trapdoor problems, or breakage if Mineflayer removes `physicTick`. | **M1 Spike B** (join, walk, disconnect). **M2 live scenario tests** on a test world: path 50 blocks, open doors, collect, craft, fight. | An adapter layer hides the plugins. Exact pins. `patch-package` with a reproducing test and an ADR. Mindcraft's MIT patches as reference. Our own combat module by M5–M6. Our own movement handling if pathfinder blocks progress. |
| 6 | **Version drift:** a launcher update, a server jar change or a bot dependency bump breaks the protocol. | The bot can't connect, or gets subtle desyncs. | The health check pings the server and compares the reported version with the pinned `1.21.11`. The bot refuses to start on a mismatch. | Pin everything (server jar, client profile, `mineflayer`, `minecraft-data`). Upgrades go through an ADR only. |
| 7 | **Native modules on Windows** (better-sqlite3, sqlite-vec). | Install failures. | **Largely de-risked:** better-sqlite3 13 ships N-API prebuilds for win32-x64, and sqlite-vec ships a windows-x64 build (verified on Linux; see research). The M1 SQLite health check runs a real KNN query on your PC. | If sqlite-vec fails: brute-force cosine in TypeScript over a BLOB column. That is fine up to about 10⁵ vectors at 768 dimensions. |
| 8 | **Stuck states and infinite loops** (pathing forever, the same failing plan repeated). | Wasted hours, no progress. | The watchdog's progress metrics. A repeated-failure detector. The dashboard shows how long the current skill has been running. | Timeouts on every skill. Abort signals. A cooldown for repeated failures. "Danger zone" memories. A critic lesson after repeated failures. |
| 9 | **Data loss or corruption** on crash, power loss or a bad migration. | Memories and skills lost. | Crash tests: kill the process mid-write, then check integrity. A migration test against a copy of a real DB. | WAL mode, transactions, write-before-act decision records, automatic backup before each migration, `quick_check` in the health check. |
| 10 | **Structured-output support varies by model** (thinking models, gpt-oss's harmony format, Andy-4's command-trained output). | Some candidates can't produce our schema reliably. | **Spike A includes one structured-output probe** per model (cheap). M3 measures it fully. | Per-model prompt adapters behind the provider. `think` toggled per task type. Repair and fallback. Drop candidates that can't comply. |
| 11 | **TypeScript 7 tooling gaps.** typescript-eslint only supports TS < 6.1. | Lint setup friction. | M1 setup: make `typecheck` and `lint` pass from the first commit. | oxlint (type-aware through tsgolint, built on TS 7). If that proves immature: TS 6.0.3 with typescript-eslint (ADR 0003 records the fallback). |
| 12 | **One GPU shared by 5–10 agents later.** | Queue latency grows linearly, and urgent requests wait. | InferenceQueue metrics from M3 (wait time per priority and per agent). A load test with simulated agents before M8. | Priorities, deadlines and aging. Coalesce or skip redundant requests. A smaller model for background tasks. Agents act through long skills so they need fewer decisions. |
| 13 | **Server CPU and RAM with many bots on the same PC.** | Server lag (TPS below 20) that distorts bot physics. | Record server TPS through RCON (`/tick query`) from M2. Load test before M8. | View distance and simulation distance settings, server memory flags, possibly Paper later (ADR needed, since it changes behaviour). |
| 14 | **Packaging as a "standalone Windows app".** Native addons and a single-file exe (Node SEA) don't mix easily. | Install experience. | Not needed until after M5. | For now: scripts plus a dashboard served locally in the browser. Packaging options (installer, Electron or Tauri shell) get their own ADR later. |
| 15 | **GPU training on AMD/Windows for RL (M6).** | Slow training. | Analysis before M6. | Keep policies small so they train on the CPU. Use simulation to speed things up instead of GPU. |
